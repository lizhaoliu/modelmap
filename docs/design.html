01 Overview

What modelmap is

Understanding a model today means reading config.json, squinting at print(model), or digging through modeling_qwen3.py. None of those show you the shape of the network — how blocks nest, where the parameters live, what actually happens to a tensor on its way through.

modelmap is a web app that takes any Hugging Face model id — Qwen/Qwen3-8B, meta-llama/Llama-3.1-8B, openai-community/gpt2 — and renders the architecture as an interactive hierarchical graph within a few seconds, without downloading a single weight. Two modes:

  • Explore mode — a zoomable, collapsible map of the module tree. Click any node to inspect its class, parameter count, tensor shapes, and dtype. Repeated layers collapse into a single stack (“decoder block ×36”) so an 8B model reads like a diagram, not a hairball.
  • Flow mode — an animated walkthrough of a forward pass. A pulse travels the graph in real execution order while a shape readout narrates the tensor’s journey: [1, 7] → [1, 7, 4096] → … → [1, 7, 151936].

The one-line pitch: Netron’s generality, bbycroft’s delight, driven by a model id instead of a file.

02 Goals & non-goals

Scope for v1

Goals

  • Any transformers-supported repo renders from just its id, in under ~5 s uncached and instantly when cached. Text LLMs (Llama/Qwen/Mistral/GPT-2/BERT families, dense and MoE) and vision / vision-language models (ViT, Qwen2.5-VL) are the acceptance bar; anything else that works is a bonus.
  • Great UX is a requirement, not polish: 60 fps pan/zoom, meaningful zoom levels, keyboard-first navigation, shareable URLs per model.
  • Flow animation reflects the real execution order and tensor shapes, captured from an instrumented (fake) forward pass — not a hand-drawn approximation.
  • Degrade gracefully: a repo we can’t fully trace still gets a structural view.

Non-goals for v1

  • No real inference — no weights are downloaded, so no live activations or attention heatmaps. (The flow trace uses shape metadata only.)
  • No ONNX / GGUF / TorchScript file import — Netron covers that; we are id-driven.
  • No training visualization, no model editing/export, no diffing two models (a compelling v2 candidate).

04 System architecture

A thin server that never touches weights

Extraction needs transformers + PyTorch (to instantiate the module tree), which cannot run in the browser — so a small Python service does the extraction and serves a static-friendly JSON graph. The frontend is a pure SPA; all interactivity and animation are client-side. The same package also runs fully locally as uvx modelmap (serve + open browser), so the tool is useful before anything is deployed.

API surface (v1): GET /api/graph/{model_id}?revision=…, GET /api/search?q=… (proxies HF model search for the autocomplete), GET /api/health. Gated repos: the client may attach a user-supplied HF token per request; the server forwards it to the Hub and never persists it.

05 Graph extraction

Meta device: the whole trick

PyTorch’s meta device materializes tensors with shape and dtype but no storage. Instantiating a model under it costs megabytes of RAM and milliseconds of compute regardless of parameter count — an 8B or 235B model is equally free. That gives us the exact module tree transformers would build, without weights:

config = AutoConfig.from_pretrained("Qwen/Qwen3-8B")
with torch.device("meta"):
    model = AutoModelForCausalLM.from_config(config)   # full nn.Module tree, zero download

Stage 3: the traced forward

We register forward hooks on every module, then run a fake batch (meta tensors, e.g. input_ids: [1, 7]) through the model. Most PyTorch ops execute happily on meta tensors — shape inference runs, arithmetic doesn’t. The hooks record, per module call: a monotonically increasing step index, the module’s qualified path, and input/output tensor shapes and dtypes. That trace is both the edge list (who feeds whom, in order) and the Flow-mode script.

Independent signal: safetensors headers

huggingface_hub.get_safetensors_metadata(id) reads only each shard’s header via HTTP range requests — every weight’s name, shape, and on-disk dtype for a few KB. We use it to (a) attach real parameter counts and storage dtypes to nodes, and (b) serve a degraded “weights view” for repos that transformers can’t instantiate at all.

Fallback ladder

  1. Full: meta instantiate + traced forward → structure, order, and shapes.
  2. Structural: instantiation works but the forward faults on some meta-incompatible op → module tree with registration order, trace marked approximate; Flow mode still runs, labeled as such.
  3. Weights view: instantiation fails (unsupported arch, no transformers class) → tree reconstructed from safetensors tensor names alone. Explore-only.

Security note: repos with custom code (trust_remote_code) execute arbitrary Python at instantiation. Default: refuse and drop to the weights view, with a per-repo opt-in flag that only makes sense in local/self-hosted mode. The hosted extractor runs in an isolated worker with no secrets either way.

06 Graph data model

One JSON document per model

The graph is hierarchical: every node is a module keyed by its qualified path, containers own children, and dataflow edges connect siblings at each level. Nodes carry a kind from a small taxonomy — it drives color, icon, and default collapse behavior:

embedding / head attention mlp / expert norm / residual data (flow mode) 
{
  "model_id": "Qwen/Qwen3-8B", "revision": "main", "fidelity": "full",
  "params_total": 8190735360,
  "nodes": [
    { "id": "model.embed_tokens", "kind": "embedding", "cls": "Embedding",
      "params": 622329856, "dtype": "bf16", "weight_shapes": {"weight": [151936, 4096]} },
    { "id": "model.layers.0.self_attn", "kind": "attention", "cls": "Qwen3Attention",
      "parent": "model.layers.0", "params": 29368320, … }, …
  ],
  "repeats": [
    { "path": "model.layers", "count": 36, "representative": "model.layers.0",
      "signature": "sha1:a91f…" }
  ],
  "edges": [ { "from": "model.embed_tokens", "to": "model.layers.0" }, … ],
  "trace": [
    { "step": 41, "node": "model.layers.12.self_attn",
      "in": [[1, 7, 4096]], "out": [[1, 7, 4096]] }, …
  ]
}

Repeat collapsing is what keeps big models legible and payloads small. We hash each subtree’s structure (classes, shapes, wiring — not the index in its name). Runs of siblings with identical signatures are stored once, as a representative plus a count; the client renders a stack node and can expand any individual index on demand. A 36-layer model ships one layer’s subtree, not thirty-six.

07 Frontend & UX

One canvas, one inspector, one timeline

Interaction model

  • Semantic zoom. Zoomed out, only top-level stages render (embed → blocks → head) with parameter-share encoded as node height. Zooming past thresholds progressively reveals children in place — the same mental model as a map. Layout runs in a web worker (ELK, layered); expanding a node animates its children in without reflowing the whole world.
  • Collapse is the default. Repeats render as stacks; containers deeper than two levels start closed. The graph a first-time visitor sees for Qwen3-8B has ~10 nodes, not ~500.
  • Inspector. Click → class, qualified path, params (absolute and % of model), weight shapes, I/O shapes from the trace, dtype, plus a link to the defining source file on the Hub.
  • Search & command palette. ⌘K is both model search (HF autocomplete) and node search (“q_proj” jumps and highlights all matches).
  • Shareable state. /m/Qwen/Qwen3-8B?sel=layers.12.self_attn&mode=flow&step=41 — the URL is the whole view state, so a link reproduces exactly what you’re looking at.

08 Flow mode

Animating the forward pass

Flow mode plays the extraction trace back on the graph. It is a guided replay of real execution, not a looping decoration: every frame is anchored to a trace step with true module order and tensor shapes.

  • The pulse. An amber particle travels edge paths between consecutive trace steps; the active node lifts (glow + slight scale), spent nodes cool to a faint warm tint so progress reads at a glance. Residual-add joins show two pulses merging — the detail that makes transformer topology click.
  • The shape narrative. A persistent chip above the timeline morphs the tensor spec at each hop — [1, 7] → [1, 7, 4096] at embed; at attention, the head split [1, 7, 4096] → [1, 32, 7, 128] — with a one-line plain-language caption per node kind (“project into 32 query heads of 128 dims”). Captions are templated per taxonomy kind + config values, so they generalize across models without per-model authoring.
  • Timeline. Play/pause, scrub, ←/→ stepping, 0.5–4× speed. Steps inside collapsed stacks compress: the pulse loops the representative block with a “layer 12 / 36” counter, so 36 layers take ~10 s, not 3 minutes. Camera gently follows the pulse (off by default when zoomed out; always off under prefers-reduced-motion, which also swaps the moving pulse for stepped highlighting).
  • Attention micro-view. Expanding an attention node during flow plays its inner choreography: Q/K/V projections fan out in parallel, scores form [1, 32, 7, 7], softmax, weighted sum, output projection. One hand-tuned sub-animation per taxonomy kind (attention, MLP/GLU, MoE router, norm) — reused everywhere, since kinds are shared across model families.

Implementation: a single rAF-driven timeline (elapsed time → fractional trace position) with pulses as SVG circles on measured edge paths — no per-step React re-render; only the inspector and chip re-render on step boundaries. This is the part most at risk of jank, so M3 starts with a performance spike, and every effect must justify itself against the 60 fps budget.

10 Performance & scale

Budgets, and the model that breaks naive rendering

Order-of-magnitude module counts: GPT-2 ≈ 150 · Qwen3-8B ≈ 500 · Llama-3.1-70B ≈ 900 · Qwen3-235B-A22B ≈ 36 000 (94 layers × 128 experts × 3 projections). The MoE case is the design constraint: rendering it flat is unusable in any engine, which is why repeat-collapsing lives in the data model (§06), not the view — experts hash identically, so 128 of them ship and render as one stack.

  • Payload budget: ≤ 300 KB gzipped graph for the worst public model (repeat-collapsing makes payload scale with unique structure, which is small everywhere).
  • Render budget: ≤ 300 nodes mounted at any moment — enforced by collapse-by-default + semantic zoom + React Flow’s onlyRenderVisibleElements. Expanding past the budget auto-collapses the furthest-away container (with a toast, never silently).
  • Server budget: uncached extraction ≤ 5 s p95 (meta instantiation is fast; Hub metadata fetches dominate). Cache popular models warm; extraction runs in a worker process with a hard timeout so a pathological repo can’t wedge the API.

13 Decisions

Resolved 2026-08-14

  1. Deployment target: local and hosted. uvx modelmap from day one; the same container ships to a hosted public site in M4, with the sandboxed extractor from §05 as a hard requirement.
  2. Educational captions: core. The plain-language shape narrative in Flow mode (§08) lands with M3, not as a later nice-to-have.
  3. v1 model families: multimodal included. ViT and Qwen2.5-VL join the acceptance set alongside text LLMs, BERT, and MoE.
  4. Name: modelmap (was hviz) — package, CLI, repo, and site. PyPI-available at decision time.
  5. Post-build (2026-08-15/16): a CSS 2.5D tilt was prototyped and rejected — depth encoded nothing the 2D containment cues didn't already show. Any future 3D work stays scoped to a Flow-mode replay scene where physical tensor proportions would be new information. Hosting hardening measured and built (torch-free parent ≈50 MB, pre-gzipped cache, de-dup, back-pressure, rate limit, worker rlimits, container with dropped capabilities); deployment target intentionally left open.
  6. 2026-08-19 (M7/M8): analytics are deliberately implemented twice (Python for server/CLI/MCP, TypeScript for the live UI) with shared fixture tests rather than a WASM bridge; the MCP server defaults to local extraction but can delegate to the hosted API; local paths are a loopback-only capability, never a hosted one; GGUF variants are addressed with a :label suffix on the model id so every surface (URL, REST, CLI, MCP, cache key) agrees.
14 M5 · Cost lens

From structure to cost: where compute and memory go

The map answers what is this model made of. The next question practitioners ask is what does it cost to run — and every input needed to answer it is already on the client: traced shapes, module attributes (in_features, kernel sizes), dtypes, and config (heads, KV heads, experts, top-k). So the Cost lens is a client-side derivation: no new server work, no new payload, and every number re-derives instantly when you change the assumptions.

What is computed

MetricFormula (per module)Source
Compute (MACs)Linear / Conv1D: tokens × in × out · Conv: out_elems × in_ch/groups × kernel · attention core (analytic, per attention node): 2 × B × heads × T² × head_dim · MoE: only k / E of expert MACs are active · elementwise ops (norms, activations): elements, shown as “other”traced shapes, attrs, config
Parameter memoryparams × bytes(dtype); MoE additionally reports active params per token = dense + k/E × expertsnode params, dtype
Activation memoryoutput tensor bytes at the chosen T / B / dtype; per-module and the largest single activation (attention scores at long T)traced shapes
KV cacheper token: layers × 2 × kv_heads × head_dim × bytes (MLA: kv_lora_rank + rope_dim; hybrid linear-attention layers excluded)config

Roll-ups: containers sum their children; repeat stacks multiply by count. Every metric is labeled an estimate with its formula one hover away — modelmap never claims kernel-level accuracy, only the analytic count that architecture papers quote.

Scaling shapes: the what-if bar

Traced shapes are for the dummy input (B=1, T=7). The dim labeler already knows which dims are batch and seq by value-matching; the what-if bar substitutes new values into those dims (attention scores [B, h, T, T] scale quadratically because both dims are seq) and re-derives everything. Controls: sequence length (log slider, 1 – 128k), batch, dtype. Assumptions sit in the URL, so a shared link carries them.

Acceptance

Qwen3-235B-A22B reports ≈ 22 B active parameters per token (the “A22B” in its name) and Qwen3-8B ≈ 8 B; per-token compute lands within 10 % of the standard 2 × active params rule for dense models; the T slider makes attention’s share visibly grow toward long context; every metric hover shows its formula. Ships as a lens toggle so the default view is unchanged.

15 M6 · Compare

Two models, aligned, differences first

The second most-asked question about a model is how does it differ from that other one — a base vs its fine-tune, Qwen2.5 vs Qwen3, Llama vs Mistral at the same size. Compare loads two graphs side by side, aligns them structurally, and makes the differences the loudest thing on screen. It is entirely client-side (two graph fetches; the server is untouched), and its summary rows reuse the Cost lens, which is why M5 comes first.

Alignment

  1. By path. Modules with identical qualified names pair up. Because Hugging Face naming converged (model.layers.N.self_attn.q_proj is the same in Llama, Qwen, Mistral, Gemma), this alone aligns most of two same-era LLMs and all of a base/fine-tune pair.
  2. By role. Unpaired modules pair with an unpaired sibling of the same kind and position (wte ↔ embed_tokens, c_attn ↔ the QKV projections as a group).
  3. Repeat stacks compare representative-to-representative plus counts (×32 vs ×36), and the structural signature says at a glance whether the blocks are the same design.
  4. What is left is added or removed.

For each pair, the diff is over the facts modelmap already holds: params, dtype, weight shapes, traced I/O shapes, attributes (eps, bias), kind and class, repeat counts — plus the config keys that matter (heads, KV heads, hidden, ffn, vocab, context, rope theta, experts/top-k, tied embeddings).

The screen

  • Route /compare/{A}...{B} (revisions via @rev). Both models load in parallel with the same loading overlay; a picker on the landing gallery and a “compare with…” action in the top bar get you there.
  • Two canvases with linked pan/zoom, linked expansion (expanding a paired node expands its twin), and linked selection. Nodes carry a diff mark: unchanged pairs dim to 55 % opacity, changed pairs get the amber outline, added/removed get a dashed border and a +/− chip. A “differences only” toggle collapses unchanged subtrees.
  • Diff inspector — one panel, two columns, row-aligned facts; changed cells amber, missing cells struck. Config deltas up top.
  • Summary strip — params, layers, heads / KV heads, hidden, ffn, vocab, context, compute/token and KV/token from the Cost lens, and the count of changed / added / removed modules.
  • Flow mode is disabled in Compare (two pulses is noise); the inspector’s traced shapes still show for both.

Acceptance

Qwen2.5-7B vs Qwen3-8B: every layer module aligns, the diff calls out q_norm/k_norm added, projection biases removed, ffn 18 944 → 12 288, and 28 → 36 layers. gpt2 vs gpt2-medium: identical design, only widths and counts change (all pairs by path). A base and its instruct fine-tune: zero structural differences reported. Two unrelated models still render usefully with most modules unpaired rather than mis-paired.

16 M7 · Export & integrate

Leaving the page: the same facts in every workflow

A map that only lives in one browser tab is a demo. Once the graph document exists, everything derived from it — the picture, the per-module table, the cost numbers, the diff — should be reachable from wherever the work actually happens: a README, a design doc, a capacity spreadsheet, a Slack thread, a coding agent. M7 adds those surfaces without inventing new data: each one renders the document (§06) or its analytics (§14) in another format.

Surfaces

  • Images of this view. export ▾ → PNG / SVG renders the current canvas — the same ELK positions, fixed node sizes and bezier edges the canvas uses — into an SVG string on the client (no DOM serialisation, no font embedding problems), with the active lens badges, heat and selection; PNG rasterises it at 2× (capped at ~16 Mpx). The file is what the user saw, at the current expansion state.
  • Data. CSV — one row per shipped module (path, kind, class, repeats, multiplicity, params with repeats, dtype, weight / traced shapes, MACs per token, weight / activation / KV bytes, attributes, source link); Markdown — a model-card style summary (headline numbers, config table, stacks, cost at T/B/dtype, largest weights); JSON — the document itself; Graphviz DOT — clusters to a depth, edges in execution order. CSV/MD/DOT come from the server (/api/export) so the CLI, REST and UI are byte-identical; JSON and images are produced client-side.
  • Links. Every node's inspector has copy link (?sel=), the export menu copies the view URL, an <iframe> snippet, or the API URL. ?embed=1 renders chrome-less (no top bar, no inspector, an attribution badge that opens the full page; all other URL state — selection, lens, flow — still applies). API responses keep X-Frame-Options; the SPA may be framed anywhere.
  • REST. /api/summary/{id} (headline numbers + cost at T/B/dtype), /api/export/{id}?format=, /api/plan/{id} (§17), /api/compare?a=&b= (§15 server-side), plus the existing graph / gallery / search. All GET, CORS-open, OpenAPI at /docs; model ids accept owner/name[:variant] (§18).
  • Python & CLI. from modelmap import extract_graph, summarize, plan_serving, align, render; modelmap dump -f csv|md|dot, cost, plan, diff. import modelmap stays torch-free.
  • MCP server. modelmap mcp (stdio; --remote https://modelmap.cc to delegate to the hosted API so the agent's machine never needs torch) exposes describe_model · estimate_cost · plan_serving · compare_models · list_modules · search_models · export_markdown. Every tool takes the same assumptions (T, B, dtype) the UI shows and returns the same numbers.
  • Hub integration. A Chrome extension and a userscript add a view in modelmap ↗ button next to the model name on huggingface.co (pure DOM, no permissions).

Twin analytics

Cost (§14), the planner (§17) and compare alignment (§15) now exist in Python as well as TypeScript — deliberately duplicated rather than shared, because the UI must re-derive instantly on the client and the server must answer without a browser. tests/test_analytics.py and web/tests/*.test.ts pin the same fixture numbers (Qwen3-235B ≈ 22 B active params, Qwen3-8B KV = 36 × 2 × 8 × 128 × 2 bytes/token, tied lm_head stored once, …) so the two cannot drift silently.

Acceptance

From a model page: PNG and SVG downloads reproduce the current expansion and lens; CSV has a row for model.layers.0.self_attn.q_proj with multiplicity 36; the embed snippet renders chrome-less with the badge; a node's copied link reopens the model with that node selected. curl /api/summary, modelmap cost and the inspector agree on KV bytes at T; the MCP tools register with schemas and answer from the same document.

17 M8 · Serving planner

Will it fit, and how would I split it?

The question behind most visits from people who self-host is not "what is the architecture" but "does this fit on what I have, at the context I need". The Cost lens already knows weight bytes at stored dtypes, KV bytes per token per layer, and the largest activation at T and B; the planner arranges those across GPUs.

  • Inputs — GPU count, memory per GPU (presets for H100/H200/A100/L40S/L4/4090/…, or custom), tensor-parallel and pipeline-parallel degree (kept consistent with the GPU count), headroom (fraction reserved for framework workspace / fragmentation), and the shared T / B / dtype assumptions.
  • Placement — the largest repeat stack is the layer stack; stages get contiguous layer ranges balanced by weight bytes, the embedding joins the first stage and the head the last (a two-stack model like DeepSeek-V3 places all 61 layers; a model without a stack splits its top-level modules). TP divides weights, KV and activations per stage. Activations are the largest single non-logits tensor (prefill peak; decode needs far less; logits excluded because engines compute them for sampled tokens only).
  • Outputs — per stage / per GPU: weights, KV at T, activation, total, fits (≤ capacity × (1 − headroom)); bytes crossing each pipeline boundary per forward (B × T × hidden × bytes); the KV-limited maximum context at this batch; notes when heads don't divide across TP or KV heads are fewer than TP ranks (K/V replicate).
  • Where — fit? in the top bar (state in the URL and localStorage), modelmap plan, /api/plan, the MCP plan_serving tool.

18 M8 · Quantized and local checkpoints

The variant you will actually serve

Self-hosters run the Q4_K_M, the FP8, the AWQ — not the bf16 reference. Those repos were either filtered out (trending) or shown at the wrong bytes. M8 makes quantized checkpoints first-class and lets the same tooling run on checkpoints that never leave your machine.

  • GGUF without downloading. A GGUF file begins with a self-describing header (key/value metadata and the tensor table); the tokenizer vocabulary makes it a few MB, the tensor data many GB. gguf.py reads the header through HTTP range requests, maps the metadata onto a transformers config (reusing transformers' own GGUF_CONFIG_MAPPING; output.weight present ⇒ untied head; causal-LM class named so the tree carries lm_head), instantiates on the meta device and traces the forward exactly like a safetensors repo, then applies each tensor's ggml quant type to its module through the standard llama.cpp names (blk.N.attn_q → model.layers.N.self_attn.q_proj, ffn_*_exps → mlp.experts). Unknown architectures fall back to a weights view built straight from the tensor table. Bits per weight (Q4_K 4.5, Q6_K 6.56, Q8_0 8.5, IQ2_XXS 2.06, …) feed the Cost lens, so weight bytes are true on-disk bytes; a note reports the file's total and whether quant types vary per layer.
  • Variants. A repo's *.gguf files group by quant label (shards of one variant together); the document carries variant and variants, the top bar shows a picker, and owner/name:Q8_0 addresses a variant everywhere (UI, REST, CLI, MCP). Default Q4_K_M when present.
  • Other quantization. Safetensors repos with a quantization_config (FP8, AWQ / GPTQ int4, bitsandbytes, compressed-tensors, MXFP4) label packed weights with the quantized dtype; per-module dtype now comes from the weight tensor (scales and zero-points no longer overwrite it), and per-expert checkpoint tensors resolve to the fused experts module — a 235B FP8 repo reports ≈ 223 GB of weights, not 434.
  • Local checkpoints. local:/path ids (CLI: any existing path; modelmap ./ckpt opens it in the browser) read config.json / safetensors headers / GGUF headers from disk; never cached, never enabled on the hosted site (MODELMAP_ALLOW_LOCAL). Compare a fine-tune against its base with the same diff.
  • Interleaved repeats. The collapser's second pass groups leftover siblings by signature regardless of adjacency, so DeepSeek-V4's alternating sliding-window / compressed-attention layers collapse into ×43 — 2 repeated designs (×20, ×20) + 3 unique instead of 43 loose blocks; stack badges count every child, opening a stack opens one block of each design, and the inspector lists interleaved members.

accepts when Qwen/Qwen3-8B-GGUF opens as Q4_K_M with a picker of 5 variants, q_proj reads "Q4_K · 4.5 bpw", and switching to Q8_0 re-extracts with ≈ 7.5 GB of weights; Qwen3-235B-A22B-FP8 reports ≈ 223 GB; a local directory holding only gpt2's config.json renders at full fidelity; DeepSeek-V4-Flash's layers collapse.
